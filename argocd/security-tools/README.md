# Security tools

This directory installs independently managed security tools. Helm charts
and supporting Kustomize resources are generated by the existing
`infra-security-helm` and `infra-security-kustomize` ApplicationSets.

| Argo CD application | Namespace | Runtime model | Persistent storage |
| --- | --- | --- | --- |
| `security-sonarqube`, `security-sonarqube-config` | `security-sonarqube` | SonarQube Community Build, PostgreSQL, suspended scanner CronJob | SonarQube `1Gi`; PostgreSQL `500Mi` |
| `security-trivy`, `security-trivy-config`, `security-trivy-operator`, `security-trivy-dojo` | `security-trivy` | Trivy server, native workload discovery/rescanning, reports, and DefectDojo ingestion | Disposable `2Gi` cache |
| `security-nuclei` | `security-nuclei` | Six-hourly DAST CronJob with DefectDojo ingestion | None |
| `security-zap` | `security-zap` | Stateless ZAP daemon/API for CI-triggered DAST | None |

The SonarQube CronJob remains a dormant template. Trivy Operator discovers
deployed workloads and refreshes their vulnerability reports every 24 hours.
Nuclei runs at
00:00, 06:00, 12:00, and 18:00 Europe/Istanbul time and never consumes GitHub
runner CPU. Each Nuclei Job writes JSONL to a size-limited `emptyDir`, uploads
it directly to DefectDojo over the cluster network, and discards the local copy
when the Job is deleted. DefectDojo is the persistent report system.

## Storage profile

The home-lab profile intentionally favors a small, disposable footprint:

- Longhorn's global default of two replicas applies to all three claims.
- The `security-sonarqube` quota permits exactly the declared `1Gi + 500Mi`
  claims (with 12 MiB of unit-conversion headroom) and prevents a third claim.
- SonarQube uses its own embedded Elasticsearch. Its indexes are rebuildable;
  no backup or recurring Longhorn snapshot is configured.
- SonarQube logs rotate at 1 MB with two retained files per log family and HTTP
  access logs disabled. This keeps the log footprint well below 50 MB.
- PostgreSQL WAL is bounded for the 500 MiB claim and collection of database
  logs into files is disabled.
- Prometheus warns when either SonarQube or Trivy has less than 15% free space.
- Every `emptyDir` used by the scanners has a `sizeLimit`, and every container
  has an ephemeral-storage limit.

These limits are intentionally aggressive. If SonarQube reaches its disk
watermark, delete its disposable claim and let Argo CD rebuild it; do not grow
the claim without also changing the namespace quota.

## Credentials

SonarQube credentials are deliberately not managed by Argo CD. Create the
runtime-only Secret manually after the `security-sonarqube` namespace exists
and before syncing the SonarQube applications:

```bash
kubectl -n security-sonarqube create secret generic security-sonarqube-credentials \
  --from-literal=postgres-password='<strong-random-password>' \
  --from-literal=monitoring-passcode='<strong-random-passcode>'
```

Argo CD does not track or prune the manually created Secret. Change the default
SonarQube `admin` password interactively in the UI; the administrator password
is not stored in Kubernetes or managed by GitOps.

After SonarQube is healthy, create the `podinfo-emrah` project and generate a
project analysis token in **User > My Account > Security**. Store its exact
value in a second runtime-only Secret:

```bash
kubectl -n security-sonarqube create secret generic security-sonarqube-scanner-token \
  --from-literal=token='<token>'
```

If the credential Secret is lost while PostgreSQL's PVC remains, a newly chosen
password will not match the password stored in PostgreSQL. Because this profile
treats the data as disposable, delete both SonarQube PVCs, recreate the
credential Secret, and sync `security-sonarqube-config` and
`security-sonarqube` again.

## Manual scans

Create a one-off Job from any suspended CronJob:

```bash
kubectl -n security-sonarqube create job --from=cronjob/security-sonarqube-scan security-sonarqube-scan-manual
kubectl -n security-nuclei create job --from=cronjob/security-nuclei-scan security-nuclei-scan-manual
```

Use a unique Job name for subsequent runs. Namespace traffic is intentionally
unrestricted at this troubleshooting stage.

## Trivy Operator running-image vulnerability flow

`security-trivy-operator` watches deployed Kubernetes workloads and creates
native `VulnerabilityReport` resources. Its short-lived scan Jobs use the
existing `security-trivy` service in client/server mode; they do not contain a
custom inventory or report parser. Reports have a 24-hour TTL, so unchanged
workloads are periodically rescanned against refreshed vulnerability data.
Scan concurrency is limited to one for the homelab.

The Trivy server owns the main vulnerability database in its disposable
Longhorn cache and is configured to update it from Aqua's database registry.
The Operator's client image is pinned to the same Trivy release as the server.
Java database data needed by a client scan remains ephemeral.

Reports contain HIGH and CRITICAL findings and include CVSS fields. The
`security-trivy-dojo` watches those native reports and imports them with
DefectDojo's `Trivy Operator Scan` parser. The Asset is `Kubernetes runtime
image vulnerabilities - homelab cluster`; each Kubernetes namespace becomes
an Engagement, and each stable workload/container identity becomes a Test. A
ReplicaSet's rollout hash is removed from that identity. This makes the UI
navigable and scopes `close_old_findings` to one workload/container service.
The importer sends a small superset to DefectDojo: every numeric CVSS 9.0+
finding is present, while some HIGH findings below 9.0 remain available for
investigation. PagerDuty is more selective and uses the Operator's
`trivy_vulnerability_id` metric to match numeric scores from 9.0 through 10.0.

DefectDojo `close_old_findings` is enabled with a caller-supplied stable service
identity made from namespace, workload, and container. Trivy Operator is
explicitly limited to current Deployment revisions. Before the first grouped
import, remove reports owned by zero-replica historical ReplicaSets; this
prevents an old report created before current-revision filtering from becoming
the last reimport for a stable workload Test.

Before syncing, permit the `security-trivy/vault-auth` ServiceAccount in the
existing Vault Kubernetes role `vso-admin`. Create a dedicated DefectDojo
Open Source user named `trivy-dojo`, authorize it on the runtime-image Asset,
and store its API token in `kv/security/defectdojo/credentials` as
`trivy-dojo-api-token`. VSO creates
`security-trivy-dojo-defect-dojo-api-credentials`, containing `apiKey` and the
internal DefectDojo URL expected by the report-operator chart.

Observe initial operation with:

```bash
kubectl -n security-trivy get deploy,pods,jobs
kubectl get vulnerabilityreports.aquasecurity.github.io -A
kubectl -n security-trivy logs deploy/security-trivy-operator
kubectl -n security-trivy logs deploy/security-trivy-dojo-operator
```

Confirm the reports appear in DefectDojo and that Prometheus exposes
`trivy_vulnerability_id` with `vuln_id`, `vuln_score`, `image_digest`, and
workload labels. `TrivyRunningImageCVSS9` is initially observation-only: it has
`paging: disabled` and deliberately lacks `team: security`. After a controlled
vulnerable-image test proves the metric, DefectDojo import, alert grouping, and
resolution behavior, replace `paging: disabled` with `team: security` in
`trivy/base/prometheusrule.yaml`. The existing Alertmanager route will then
open and resolve one PagerDuty group per vulnerability ID and image digest.

## Nuclei report ingestion

Create a dedicated DefectDojo API token and add it to the existing Vault record
`kv/security/defectdojo/credentials` as field `defectdojo-api-token`. The Vault
Secrets Operator materializes only that field as the
`security-nuclei-defectdojo` Secret. Do not put the token in Git.

Nuclei scans `podinfo.lab-a-dev.svc.cluster.local:9898` every six hours for low,
medium, high, and critical findings. Reports are reimported into the shared
Asset `Application CI/CD security findings - homelab`, application engagement
`Podinfo`, and test `Nuclei recurring lab-a-dev`. The Podinfo CI scanners and
the Falco and Kyverno exporters must use the same Asset and engagement; each
scanner remains a separate Test below that engagement. Add future applications
as separate engagements rather than creating application-specific Assets. Each
application-scoped exporter must filter its input to that application; the
current Falco and Kyverno exporters include only Podinfo workload resources.
Each execution has a timestamped build ID;
`close_old_findings=true` lets DefectDojo reconcile fixed and recurring
findings while preserving scan history. The uploader bootstraps a missing test
with `import-scan` and uses `reimport-scan` thereafter. Uploads are not retried
automatically because repeating a non-idempotent import can duplicate scan
history when the server accepted the request but its response was interrupted.
The upload uses DefectDojo's canonical `dojo.no-name.win` HTTP Host while
connecting directly to the internal Kubernetes Service, satisfying Django's
allowed-host validation without exposing the scan through Cloudflare.

## ZAP API

ZAP runs continuously as a single stateless daemon. CI controls scans through
the internal endpoint `http://security-zap.security-zap.svc.cluster.local:8080`.
The Gateway API exposes only `ci-zap.no-name.win` as the CI API endpoint. It
rewrites the backend authority to ZAP's reserved `zap` hostname so the shared
API/proxy listener handles requests locally. Protect this hostname with a
Cloudflare Access service-token policy before use. Security findings and scan
history belong in DefectDojo rather than a public ZAP route.

Before syncing `security-zap`, create a random API key in Vault at
`kv/security/zap/credentials` with the field name `api-key`. VSO materializes it
as `security-zap-api-key`; the key is never stored in Git.

The GitOps-managed Automation Framework plan is mounted at
`/zap/automation/podinfo-lab-a-dev.yaml`. It limits the traditional spider to
one thread and three minutes and limits the active scanner to one thread, two
minutes per rule and fifteen minutes in total. CI retrieves the plan progress
and alerts through the ZAP API and stores them as GitHub Actions artifacts. ZAP
uses disposable `emptyDir` storage only; restarting the pod intentionally
discards sessions and scan history.
